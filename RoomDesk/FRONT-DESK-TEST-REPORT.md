# 单前台酒店场景测试报告

测试日期：2026-10-04。结论：现有房态原型的核心业务场景通过；尚不能据此认定达到完整酒店前台营业系统的要求。

## 本次实测结果

- 新增并执行 **34 个连续业务场景，34/34 通过**，每个场景包含一个或多个检查。覆盖同房换客、重复提交、跨午夜交班、异常退出及备份恢复。
- 原有回归检查重新执行：**116 项共享 C# / SQLite 检查 + 47 项真实 HTTP / 进程检查，全部通过**。与上述场景有覆盖重叠，不应把数量理解为互不重复的业务功能。
- Mac 浏览器：**7 项页面验收通过，2 项受自动化阻塞，未计通过**。明细见下表。
- Windows WPF 项目在 Mac 上交叉编译成功；**未在 Windows 10 上运行**，不能由本次测试证明 Windows 的启动速度、界面流畅度、缩放及读卡器驱动兼容性。
- 使用独立临时数据库和虚构住客、测试密码。原预览库未加入测试数据，UI 测试前后 SQLite 逻辑内容 SHA-256 一致，测试结束已恢复原预览服务。

## 场景及验收口径

假设一位前台独自处理开班查房、散客到店、优惠报价、老客再次入住、退房清扫、维修停用、跨午夜查账和备份。测试系统含 24 间示例房；连续业务测试新增 601–603 房，避免依赖示例在住房。

价格按当前产品规则验收：**每次入住总价**，默认价格仅用于填表参考；修改默认价不影响已登记售价。账单按**北京时间的入住时间**筛选，结束时间包含所选分钟的最后一刻。金额代表售出总额，并非已收款。

## 发现并修复的问题

**缺少默认价格字段会误写为 0 元（中等影响，API 输入校验问题）。**

复现：`POST /api/rooms/{id}/price` 仅提交 `version`，没有 `price`。原 `decimal Price` 请求参数默认值为 0，接口返回成功并覆盖默认价。修改为可空价格并明确拒绝缺失值，返回“请填写房间默认价格。”。FD34 固化为回归用例；全部 34 场景及原 163 检查复测通过。正常页面的必填限制原本已存在，此修复补足接口防线。

证据：`validation/front-desk-first-run.txt` 保留修复前失败；`validation/front-desk-scenarios.txt` 保留修复后通过。修改只涉及 Mac 预览的 HTTP 请求校验，未改动 WPF 或共享计算逻辑。

## 性能观察及营业前缺口

Mac 本轮测量：27 房真实 HTTP 房态读取 30 次，中位数 **1.63 ms**、P95 **1.98 ms**；共享核心 300 房热读取 20 次，中位数 **1.74 ms**、P95 **2.04 ms**。这些仅为本机短时读取样本，不包含界面渲染、长时间运行和大量历史数据，不能等同 Windows 流畅度结论。

目前仍需明确或补齐：

1. **交班收款**：尚无支付方式、实收、押金、退款、欠款；不能把售出金额当作现金交班金额。
2. **常见住宿变更**：尚无专门换房、续住、按晚计费、同行多住客流程。不要靠重复入住规避这些业务。
3. **预订**：当前是房态标记，尚无到离店日期、预订人等完整预订流程。
4. **历史删除与对账**：当前删除会把记录移出后续账单；已导出的文件不会自动变化。正式对账宜增加作废原因、作废明细和账单留档。
5. **示例数据**：初始库含未登记住客的示例在住房。正式使用前应建立真实房间和期初状态，不能将示例数作为实际入住统计。
6. **设备与桌面**：Windows 10 启动/缩放/长时间操作、真实读卡器驱动与硬件读取、CSV 经系统保存及 Excel 打开均待实机验收。当前读卡仅为通用文本解析。

因此，建议继续用于**房态与入住登记原型验证**；正式作为唯一前台系统前，至少完成真实 Windows 验收，并补齐所需收款及住宿变更流程。
